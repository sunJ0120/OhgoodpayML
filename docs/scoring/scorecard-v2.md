# 오굿점수 v2 — 로지스틱 회귀 스코어카드

오굿점수를 **사람이 정한 가중치**에서 **데이터로 추정한 배점표**로 바꾸는 작업의 최종 정리 문서다. 작성일 2026-10-11.
Phase별 상세 기록은 [Phase별 작업 기록]({{ site.baseurl }}/scoring/phase-log)에 있다.

## 1. 용어 정의

코드 · 테스트 · 문서 전부 이 정의를 따른다.

| 용어 | 정의 |
|---|---|
| **부실 (bad)** | UCI 데이터: 라벨 `default payment next month = 1`. 오굿페이 운영(이후 단계): 결제일 후 30일 이상 미상환. **오굿페이 기준은 가정이며 정책 결정이 필요하다** |
| **정상 (good)** | 부실이 아닌 것 |
| **부실비 (bad rate)** | 어떤 집단의 `부실 수 / 전체 수` |
| **정상 오즈** | `정상 수 / 부실 수`. 점수 환산에 쓴다 |
| **부실 오즈** | `부실 수 / 정상 수` = 정상 오즈의 역수. 로지스틱 회귀의 목표에 쓴다 |
| **구간 (bin)** | 변수 값을 나눈 범위. 구간마다 부실비와 WoE를 계산한다 |
| **WoE** | `WoE_k = ln( (정상_k / 정상_전체) / (부실_k / 부실_전체) )`. 동치 표현: `ln(구간 정상 오즈 / 전체 정상 오즈)`. 양수면 평균보다 안전, 음수면 위험 |
| **WoE 보정** | 구간에 정상 또는 부실이 0건이면 두 값 모두에 0.5를 더해 계산한다 (`ln(0)` 방지) |
| **로지스틱 회귀** | `ln(부실 오즈) = β0 + Σ β_j · WoE_j`. WoE가 클수록 안전하므로 **모든 β_j는 음수여야 한다** |
| **점수** | `점수 = Offset + Factor · ln(정상 오즈)` |
| **점수 기준** | 정상 오즈 50일 때 600점, **정상 오즈가 2배가 될 때마다 +20점** |
| **Factor** | `20 / ln(2)` ≈ 28.8539 |
| **Offset** | `600 − Factor · ln(50)` ≈ 487.1229 |
| **배점** | 변수 j가 구간 b에 속할 때: `points_j,b = Offset / n − Factor · (β0 / n + β_j · WoE_j,b)` (n = 변수 개수). **모든 변수의 배점 합 = 점수** |
| **감점 사유** | 변수 j의 `해당 변수 최고 배점 − 실제 배점`이 큰 순서 |
| **스코어카드 파일** | 구간 경계, WoE, 배점, 기준값, 버전, 데이터 출처를 담은 JSON. 런타임은 이 파일만 읽는다 |

부호 관계: **WoE ↑ → 부실 오즈 ↓ → 정상 오즈 ↑ → 점수 ↑**

## 2. AS-IS → TO-BE

### 2-1. 한눈에 보기

| # | 항목 | AS-IS | TO-BE |

| 1 | 가중치 결정 | 사람이 하드코딩 (0.22, 0.18 …) | 데이터에서 로지스틱 회귀로 β 추정 → 배점표 파일 |
| 2 | 입력 표현 | 항목별 리스크 0~1 함수 (`횟수 ÷ 3`, `1 − 점수 ÷ 150` 등 근거 없는 변환) | 구간화 → 구간별 WoE |

| 6 | 감점 사유 | 리스크 × 가중치 상위 3개 | 배점 손실(최고 배점 − 실제 배점) 상위 3개 |
| 7 | 버전 관리 | 없음 | 스코어카드 파일에 `model_version`, `purpose`, `data_source`, `currency` |

| 9 | 입력 검증 | `/score`가 `payload: dict`를 그대로 언팩 → 잘못된 키면 500 | 스키마 검증, 모르는 키 · 누락 키는 422 (**이 항목만 운영 코드에 이미 반영됨**) |
| 10 | 문서 표현 | `docs/pages/ai_guide.md`: "신용점수의 일종으로 추후 사용자 분석에 활용" | "서비스 내부 한도 산정 지표이며 외부에 제공하지 않는다" (**반영됨**) |
| 11 | 관측 기간 | 12개월 | 6개월 (UCI 데이터 제약). 설정값으로 둔다 |

### 2-3. TO-BE 입력 변수 (5개)

UCI 컬럼: `PAY_0, PAY_2~PAY_6`(월별 상환 상태, 9월~4월), `BILL_AMT1~6`(월별 청구액), `PAY_AMT1~6`(월별 납부액).

|---|---|---|---|

| `on_time_ratio` | 6개월 중 정규화 상환 상태가 0인 달의 비율 | 클수록 부실비 ↓ | 일치 (60.6% → 11.6%) |
| `paid_amount_6m` | `PAY_AMT1~6` 합계 | 클수록 부실비 ↓ | 일치 (32.1% → 11.8%) |
| `avg_billed_amount_6m` | `BILL_AMT1~6` 평균 | 데이터로 확인 (단조가 아닐 수 있음) | 클수록 부실비 ↓ (25.6% → 20.0%), 차이가 작음 |
| `active_months` | 6개월 중 `BILL_AMT > 0`인 달의 수 | 클수록 부실비 ↓ | **반대**: 클수록 부실비 ↑ (20.5% → 22.7%) |

### 2-4. 상환 상태 정규화 규칙

UCI 문서는 `−1 = 정상 납부, 1~9 = 연체 개월 수`만 정의한다. 실제 데이터에는 문서에 없는 `−2`, `0`이 있다.
기본 규칙(가정): `−2, −1, 0 → 0 (연체 없음)`, `k ≥ 1 → k`. 근거는 3-1.

### 2-5. 모델에서 제외하는 컬럼 (테스트로 강제)

| 컬럼 | 제외 이유 |
|---|---|
| `SEX`, `EDUCATION`, `MARRIAGE`, `AGE` | 차별 요소. 예측력이 있어도 점수에 쓰지 않는다 |
| `LIMIT_BAL` | 카드사가 정한 한도. 우리 설계의 순환 문제와 같은 구조라 제외 (비교 사례로만 기록) |
| 연장 계열 (오굿페이) | 2-2 참고 |

이 제외는 세 겹으로 강제한다. ① 학습 변수를 만드는 단계에서 5개 변수만 남기고, ② 학습 입력 검증이 제외 컬럼이 있으면 예외를 내며, ③ 스코어카드 로더가 변수 이름에 제외 컬럼 또는 `extension` · `연장`이 있으면 로드를 거부한다.

### 2-6. 그대로 둔 것 (이번 범위 밖)

- 등급 테이블(등급점수 → 브론즈~다이아, 한도, 적립률)과 `gradePoint` 최대 200 vs 계산 150 절삭 불일치
- 한도를 오굿점수와 연결하는 작업
- 자동화평가 설명 · 재산출 · 산출 이력 저장
- 운영 `/score`를 새 엔진으로 교체 (현행 엔진은 전환 전까지 유지)

## 3. 데이터 결정 기록

### 3-1. 상환 상태 정규화 (`−2, −1, 0 → 0`)

UCI 30,000명(부실 6,636명, 22.12%)의 `PAY_0` 값별 다음 달 부실비:

| 값 | 건수 | 부실비 |
|---:|---:|---:|
| −2 | 2,759 | 13.2% |
| −1 | 5,686 | 16.8% |
| 0 | 14,737 | 12.8% |
| 1 | 3,688 | 34.0% |
| 2 | 2,667 | 69.1% |
| 3 | 322 | 75.8% |

- **근거:** `−2, −1, 0`의 부실비가 12.8~16.8%로 서로 비슷하고 연체(1 이상)와 확연히 갈린다
- **남은 의문:** `−1`(정상 납부)이 `0`보다 부실비가 약 4%p 높다. `0`은 문서에 없는 값이라 최소납부 후 이월일 가능성이 있는데, 그렇다면 `0`이 더 위험해야 한다. 이 데이터에서는 반대라서 **의미를 확정할 수 없다.** 지시서 기본 규칙으로 두었다
- `PAY_2~PAY_6`에는 값 `1`이 거의 없다 (PAY_2 28건, PAY_3 4건, PAY_5 · PAY_6 0건). `PAY_0`에는 3,688건이다
- 전체 값 분포는 [Phase 1 기록]({{ site.baseurl }}/scoring/phase-log)에 있다

### 3-2. 음수 청구액

`avg_billed_amount_6m`은 음수를 포함한 평균이고, `active_months`는 `BILL_AMT > 0`인 달만 센다 (지시서 정의 그대로). 음수 청구가 있는 고객은 평균이 낮게 나오며 가장 낮은 구간에 섞인다. **처리를 바꿀지는 결정하지 않았다** (7장 #2).

### 3-3. 기대 방향과 다르게 나온 변수

| 변수 | 가설 | 데이터 | 처리 |
|---|---|---|---|
| `active_months` | 클수록 부실비 ↓ | 클수록 부실비 ↑ (20.5% → 22.7%, 차이 2.2%p, 구간 2개) | 지시서 원칙대로 억지로 맞추지 않고 그대로 사용 |

회귀의 부호 검사가 이 변수를 통과시킨 점에 주의한다. WoE는 이미 안전한 쪽이 양수가 되도록 정의돼 있어서, 부호 검사 통과가 가설과의 일치를 뜻하지 않는다.

### 3-4. 변수 중복과 기여도 불균형

- `max_delinquency_months`와 `on_time_ratio`의 WoE 상관이 **0.936**이다. 두 변수의 최우량 구간이 정확히 같은 13,934명이다 (6개월 모두 정시 상환이면 연체 개월 수가 0이므로 동치)
- 두 β의 합이 −0.957로 −1에 가깝다. 겹치는 정보를 두 변수가 나눠 가진 결과로 **보이지만 검증하지 않았다**
- 배점 폭(최고 − 최저)이 `on_time_ratio` 58.91, `paid_amount_6m` 23.41, `max_delinquency_months` 6.86, `active_months` 3.90, `avg_billed_amount_6m` 1.58이다. 연체 정보 대부분이 `on_time_ratio` 쪽에 실려 감점 사유가 한 변수에 쏠릴 수 있다
- `avg_billed_amount_6m`은 |β| 0.17이 표준오차 0.24보다 작다. 0과 구분되지 않는다

변수 정리는 결정하지 않고 5개 모두 유지했다 (7장 #3~#5).

### 3-6. 지시서에 없어서 정한 구현 선택

| 항목 | 선택 | 대안 |
|---|---|---|
| 배점 저장 | 카드에 소수 전체 정밀도로 저장하고, 합산한 뒤 최종 점수만 한 번 반올림 | 정수 배점 (합이 공식과 최대 2.5점 어긋남) |
| 반올림 | 0.5는 올림 (파이썬 `round()`는 짝수 반올림이라 쓰지 않음) | |
| 등급 규칙 | 반올림된 점수가 처음으로 `min_score` 이상인 등급. 모든 경계 아래면 가장 낮은 등급 | 예외 처리 |
| 입력 변수 | 누락 → 예외, 카드에 없는 변수 → 예외, 유한한 숫자가 아닌 값 → 예외 | 카드에 없는 변수는 무시 |
| 입력 통화 | `score_customer`의 필수 인자. 카드 통화와 다르면 채점 전에 예외 | |
| 구간 경계 | `lower < x <= upper`, `null`은 무한대, 학습 범위 밖은 가장 바깥 구간 | |
| 구간 병합 | 단조 병합(부실비가 같아도 합침) → 최소 5% 병합. 방향은 데이터가 정함 | |
| 카드 등급 | 학습 점수 5분위로 만든 **임시** 경계, `bands_status = "draft"` | Phase 7 표를 보고 사람이 결정 |
| `/score` 입력 | 8개 필드 전부 필수, 모르는 키 거부 (기존에는 누락이 조용히 기본값으로 채워짐) | 일부를 선택 입력으로 |

### 3-7. 점수 눈금

"정상 오즈 50 = 600점"은 부실이 매우 드문 포트폴리오를 가정한 눈금이다. UCI는 부실비 22.1%라 평균 정상 오즈가 3.52이고, 이 카드의 점수는 이론상 467.6 ~ 562.3에 놓인다 (검증 중앙값 538.4). **600점 이상은 한 명도 없다.** 코드 오류가 아니라 눈금과 모집단의 차이이며, 오굿페이 실데이터로 다시 학습하면 눈금이 달라진다.

## 5. 한계

1. **UCI는 2005년 대만 신용카드 데이터다. BNPL이 아니다.** 상환 방식, 한도, 이용 패턴, 고객층이 오굿페이와 다르다
2. **성과 기간이 다음 한 달뿐이다.** 오굿페이의 "결제일 후 30일 이상 미상환"과 정의가 다르다
3. **이 카드의 배점은 오굿페이 운영에 쓰지 않는다.** 파이프라인 검증용이며, 코드에서 두 가지로 막았다
   - `purpose`가 `production`이 아닌 카드를 운영 모드로 로드하면 `ScoreCardPurposeError`
   - 입력 통화가 카드 통화(`TWD`)와 다르면 `CurrencyMismatchError`
4. **검증은 한 번의 70/30 분할이다.** 교차 검증, 기간 분할(시간에 따른 안정성), 보정(예측 확률과 실제 부실비의 일치) 확인은 하지 않았다
5. **단조 판정은 5구간 기준이다.** 더 잘게 나눴을 때의 결과는 보지 않았다
6. **공정성은 제외 컬럼 차단까지만 했다.** 남은 변수가 제외한 속성의 대리 변수가 되는지는 평가하지 않았다
7. **카드 로더는 배점이 β · WoE · 절편과 일관된지 검증하지 않는다.** 사람이 배점만 고치면 잡지 못한다
8. **변수 정리가 끝나지 않았다.** 연체 변수 중복, 가설과 반대인 변수, 구분력이 없는 변수가 남아 있다 (3-4)
9. **법적 검토는 하지 않았다.** 연장 계열 제외의 근거, 신용정보법상 개인신용평가업 해당 여부, 자동화평가 설명 요구 대응 등은 별도 검토가 필요하다

## 8. 후속 과제

### 8-1. 이번 범위에서 제외한 것 (2-6)

- 등급 테이블과 `gradePoint` 최대 200 vs 계산 150 절삭 불일치 정리
- 한도를 오굿점수와 연결
- 자동화평가 설명 · 재산출 · 산출 이력 저장
- 운영 `/score`를 새 엔진으로 교체

### 8-2. 운영 전환 (콜드 스타트)

오굿페이에는 아직 상환 이력 데이터가 없으므로 아래 순서로 진행한다.

1. **전문가 가중치 v1로 시작한다.** 연장 계열을 뺀 임시 점수식이 필요하다. 이때 현행 엔진의 연장 항목 문제가 해소된다 (0장의 주의 사항)
2. **상환 이력을 수집한다.** 결제일 상환 여부, 연체 일수, 30일 이상 미상환 여부를 변수 5개를 만들 수 있는 형태로 쌓는다
3. **오굿페이 데이터로 재학습한다.** 이 문서의 파이프라인을 그대로 쓰고, `purpose = "production"`, `currency = "KRW"`로 카드를 만든다
4. **검증 후 운영 전환한다.** 점수 구간별 부실비가 단조인지 확인하고, 등급 경계를 사람이 정한다

### 8-3. 운영 전환 전에 필요한 코드

- **오굿페이 결제 · 상환 이력에서 변수 5개를 만드는 런타임 코드.** 지금은 변수를 만드는 코드가 `training`(pandas)에만 있고, 런타임 채점기는 이미 계산된 변수를 받는다
- 운영 카드 전용 검증 (`created_at` 필수 여부, 배점 일관성 검증)
- `/score` 응답 형식과 호출자(Spring) 쪽 변경 협의

### 8-4. 법적 · 정책 검토

- 연장 계열 제외의 법령 근거 확인
- 점수의 법적 성격 확인 (서비스 내부 한도 산정 지표인지, 외부 제공 가능성이 있는지)
- 자동화평가에 대한 설명 · 이의제기 대응 설계
- 부실 정의 확정
